# PERL clinician summary workspace

## Product decision

PERL’s first release is a clinician-facing companion to e-QPASS. It reads structured, scored e-QPASS output and produces an additional summary for a licensed reviewer. It is not a consumer diagnosis engine, autonomous care planner, or replacement for the existing Findings report.

The implementation follows the latest direction in the proposal and Dolores’s correspondence: prove the summary-and-review workflow in a de-identified environment, calibrate it with counselors, measure it against human interpretation, then connect it to the existing Azure-hosted e-QPASS product only after clinical, legal, security, and reliability gates are met.

## Primary user and job

The primary user is a counselor or other qualified reviewer who currently spends roughly 15–20 minutes interpreting a multi-page e-QPASS report.

Their job is to:

1. understand the dominant scored pattern quickly;
2. see which evidence supports each inference;
3. notice uncertainty, mixed signals, and critical screens;
4. refine the narrative using clinical judgment;
5. approve a safe, useful summary or return precise calibration feedback.

## Product principles

- Evidence before eloquence. Each clinical inference links back to a scored construct.
- Human judgment is the release authority. No unreviewed narrative enters care.
- Indicator language only. PERL forms hypotheses; it does not diagnose.
- Safety cannot be summarized away. Non-zero critical screens hold approval until acknowledged by a qualified reviewer.
- Separate audiences, stable facts. Clinician, care-coordinator, and payer narratives change detail and purpose without changing underlying scores.
- Data restraint by default. This prototype uses synthetic records only and visibly rejects identifiers that are not labeled synthetic.
- Every change teaches. Edits, returns, blind comparisons, model versions, and approvals belong in an audit and calibration trail.

## Deliberately not claimed

- No real AI provider or production model is connected. The candidate gateway now has an executable startup-policy HTTPS transport, but no external call is made by default, no candidate has been selected, and only synthetic calibration can be authorized; it remains not approved for PHI or clinical release.
- No AI engine has been selected. A complete three-candidate Model Trial manifest proves only local metadata completeness; it does not verify a vendor, inspect evidence, run a provider, establish clinical performance, or record legal, privacy, security, independent-review, pilot, production, or patient-use authority. The Candidate Trial Foundry adds a predeclared 9-run/12-blind structure, not execution or outcome evidence.
- No respondent data from the supplied workbooks, PDFs, reports, or email is embedded.
- The available response workbooks were inspected only for structure. Their identifiers, dates of birth, demographics, contact data, question IDs, and response IDs are not a provider integration contract and are not model input. The two exact category/threshold workbooks named in Dolores’s October 2025 email were unavailable and their logic was not invented.
- The Independent Review Dossier packages only local synthetic evidence. It does not name an outside evaluator, accept the missing workbooks or representative case set, establish accuracy or reliability, complete clinical validation, or record a signed release decision.
- No PHI handling, HIPAA attestation, SOC 2 control, Azure deployment, EHR connection, or production identity system is present.
- No automated encrypted backup policy, monitored backup job, approved retention tier, Azure restore, or approved RPO/RTO is present. The local recovery rehearsal proves only the synthetic-store restore acceptance pattern.
- No continuous production telemetry, availability or latency service objective, security-event stream, backup-job alert, paging route, or notification acknowledgment is present. The local operational probe is point-in-time evidence only.
- No externally signed container, approved immutable Azure registry, isolated network-controlled CI builder, external vulnerability/license approval, staged environment rollback, schema rollback authority, or production operator authority is present. The local Release Candidate Foundry supplies a deterministic archive, exact manifest, SBOM, provenance, configuration contract, offline verifier, and external-signature seam; the Release Admission Laboratory executes the exact archive and stores local qualification evidence; the separate rollback rehearsal still proves only compatibility of a working-tree engineering baseline.
- No authoritative e-QPASS delivery connector, PDF merge, remote attachment acknowledgement, worker identity, or production dead-letter alert is present. The connector seam is executable only under explicit synthetic-calibration authorization and can never claim that an attachment occurred.
- Sandbox quality metrics are descriptive engineering evidence; they are not clinical study results.
- The deterministic draft engine demonstrates the product contract. It is not clinically validated.
- Acknowledging the demo safety gate is not equivalent to conducting or documenting a real risk assessment.

## Source synthesis

The brief was derived from the July 2026 Blue Fractal proposal, Dolores’s forwarded correspondence from July 2025 through March 2026, the PERL meeting notes and overview deck, the example QPASS clinical summary, e-QPASS feature/validity material, the QPASS manuals and sample report package, data-export schemas, and the Focused Future board-materials master summary.

The source set contains older consumer-report experiments and earlier naming variants. The governing decisions for this build are:

- use “PERL,” never “PEARL”;
- ship the clinician summary workflow before the broader direct-to-consumer experience;
- preserve the validated scoring system rather than asking a language model to rescore raw answers;
- plan production deployment inside the existing Azure/SOC 2 e-QPASS environment;
- keep model-generated language subordinate to clinical review.

## Acceptance criteria for a clinical beta

A beta should not start until:

- a clinical lead approves the summary template, prohibited language, and risk behavior;
- the three-session Counselor Lab produces signed language/safety, blinded workflow, and reference/protocol-freeze outputs from a named qualified panel;
- a representative, de-identified calibration set is approved for use;
- a gold-standard human interpretation exists for the beta set;
- model output is versioned and reproducible;
